# ADR 0012: MIDI device layer on a timestamped, realtime-safe engine contract

- **Status:** proposed 2026-10-18
- **Date:** 2026-10-18
- **Implementation:** none yet. The epic starts after the UI slices, once the gates marked "before" below pass.
- **Reopen when:** midir cannot deliver usable arrival timestamps on Windows (WinMM or WinRT) and a different backend is needed; or a gate below proves unmeasurable on the reference machine and must be redefined; or upstream SoundCraft lands its own MIDI device layer that we should converge with instead.
- **Credit:** the prerequisite gates come from an independent engine foundation audit of `transit` (findings F01 to F10, section "MIDI readiness gates for ADR 0012"), verified at source level against `transit` d469e8f in a triage of the audit.

## Context

The engine on `transit` has no MIDI device layer. No MIDI I/O crate is in `Cargo.lock` (`crates/midi` is sequence and SMF data only). Instrument tracks show "MIDI in" only, and `setup.midi_input_devices` stores names. MIDI reaches instruments today in two ways: clip notes, which the mix schedules with sample offsets, and `Player::note(track, pitch, velocity)`, which the on-screen keyboard uses. `Player::note` carries no timestamp, no channel and no device; `MixEngine::live_note` plays it at offset 0 of whatever block drains it next (`crates/playback/src/lib.rs:1036`, `crates/mix/src/lib.rs:533`).

The epic is planned after the UI slices: a new crate `transit-midi-io` beside `audio-io`, backed by midir (WinMM or WinRT on Windows, ALSA or JACK on Linux, CoreMIDI on macOS); device enumeration and hot-plug; per-track input selection; monitored input to the armed instrument track, timestamped and placed into the audio callback's block; MIDI clip recording; MIDI learn (CC and 14-bit CC, pickup and scale); transport control (MMC, Mackie transport buttons, generic CC); MIDI clock in and out. Test hardware is an Arturia KeyStep Pro, over USB and DIN, as clock master and follower.

The engine audit concluded that the MIDI layer should not be built on the current runtime contract. The triage confirms nine of its ten findings at source level, with one partly refuted detail, and splits them: a few must hold before MIDI work depends on them, and the rest are quality work that can land in parallel. The key point for MIDI is F06: the audio callbacks discard their timestamps, and there is no mapping between host time, device frames and session samples. A midir wrapper around today's note API would inherit up to one buffer of placement error and could not recover the arrival time it threw away. The device timestamps themselves are limited: in the pinned CPAL 0.16 backend, ASIO capture and playback times are the callback time minus or plus one buffer, and WASAPI output presentation is also an estimate (annex and triage).

## Decision (outline; to be completed before the epic starts)

1. **Transport adapter, not timing architecture.** `transit-midi-io` wraps midir for ports, hot-plug and raw bytes with the backend's arrival timestamp. It owns no musical timing.
2. **One clock.** The audio device clock drives the sample timeline. The engine keeps an explicit mapping from monotonic host time to device frame time to session sample time, with a generation number that changes on device restart or reconfiguration. MIDI arrival timestamps are mapped into it. Session samples, monotonic render frames and musical beats stay distinct, so stop, seek, loop, tempo change and device restart each have a defined meaning.
3. **Timestamped event format.** Events crossing into the realtime path carry device, port, channel, note identity, arrival time and a block offset. Queues are bounded and preallocated. Releases (note-off, sustain-up, all-notes-off on disconnect) are protected under overflow. Parameter edges are not coalesced unless their semantics allow it. Overflow is counted and visible.
4. **Placement.** The callback places each event at its block offset, delayed by an explicit lookahead budget stated in frames (not "one callback", since callback sizes vary), so offsets are not negative while arrival delay and clock uncertainty fit the budget. Placement is relative to the device's reported timestamp, as mapped by the calibrated clock contract. That timestamp's quality depends on the backend; on ASIO and WASAPI it is estimated, not measured. Events that arrive too late for the budget render at the earliest legal offset and are counted. Their recorded time keeps the original arrival. The UI shows the timing quality and its uncertainty per device. Recorded notes use the arrival time mapped to session samples, not the time the block drained. Backend arrival time is not the physical keypress time.
5. **Output and clock.** MIDI out and MIDI clock out are scheduled against the same clock by a timed scheduler or backend scheduling, never by an egui repaint or a sleep loop.
6. **Ownership.** MIDI devices live in a non-UI runtime owner, not in `ui-studio/src/host.rs` or `ui-egui`. The runtime owner decision (gate G6) is made before the epic; the full move of the host orchestration out of the two front ends can land during it.
7. **Everything is a command.** `midi.input`, `midi.learn`, `midi.map`, `transport.midi_clock`, one undo step each.

## Consequences

- The epic starts later than "right after slice 5": G1 to G4 and the G6 decision come first. G1 and G3 are small; G2 is small to medium; G4 is a design task plus a test harness.
- Live MIDI monitoring gets a fixed lookahead latency on top of the device latency, in exchange for bounded jitter. The bound holds only while OS delivery delay and clock uncertainty fit the budget. Late events are counted, not hidden. For scale, a 128-frame budget at 48 kHz is 2.7 ms. On Windows, MIDI timestamps are millisecond-granular, and ASIO and WASAPI device timestamps are estimates, so the achievable precision is stated per backend, not promised as sample-accurate.
- The engine telemetry API (`Player::callback_telemetry()`) is the source for a UI follow-up that shows max load, deadline overruns and backend errors with those labels.
- The note API changes shape. `Plugin::note_on/note_off` gain channel and note identity (or a new event entry point), which touches `dsp`, `vst3-host`, `clap-host` and `mix`. Upstream offers need care: this is a trait change.
- `crates/midi` (sequence data) and `transit-midi-io` (devices) stay separate crates.
- Gates G9 to G12 do not block MIDI. They are tracked in the triage.

## Reference machine MIDI inventory (2026-10-19 11:05)

Observed with Get-PnpDevice and WinMM enumeration: the KeyStep Pro is on USB (VID_1C75&PID_0218) through Arturia's Thesycon driver (TUSBAUDIO_ENUM), with WinMM ports "KeyStep Pro MIDI IN" and "KeyStep Pro MIDI OUT". Also present: a Bluetooth LE MIDI dongle (WinMM in and out) and Windows MIDI Services (MIDI 2.0 service, virtual and loopback devices, "Service Test Loopback A/B", not visible through WinMM). Consequences: (1) G-level timing evidence uses the KeyStep over USB, not a BLE dongle, whose connection interval adds milliseconds of latency and jitter; (2) device enumeration in transit-midi-io must be checked against Windows MIDI Services, which changes how ports appear to WinMM and WinRT clients; (3) the Service Test Loopback A/B pair is a candidate for a hardware-free loopback test of arrival timestamps.
